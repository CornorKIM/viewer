# step-sender — 단계 하나를 그날 한 번만 정상 저장되게 보내고, 보낸 것은 모두 이력에 남긴다

> 상태: 사람 확정 · 독자: 구현자 / 오케스트레이터
> 산출물: sf-daily
> 이음새: 단계 보내기 → `sf-daily/api/step-sender.md` · 로그수집 API → `interfaces/sf-log-api.md` · 전송 이력 → `interfaces/sf-log-history.md` · 업체 명부 → `sf-daily/spec/companies.md`
> 단언: 같은 자리의 `tests/sf-daily/step-sender/GATES.md`

## 목적 / 의도

업체 하나 · 그날 하나 · 단계 하나에 대해, 보내도 되는지 확인한 뒤 사업관리시스템에 로그 한 건을 보내고 그 결과를 전송 이력에 남긴다. 같은 단계가 그날 이미 정상 저장됐으면 보내지 않고, 지난 날짜의 로그를 보내지 않으며, 앞 단계가 그날 정상 저장되지 않았으면 보내지 않는다.

## 언어 · 런타임

Node.js(ES 모듈).

## 의존 도구 · 시스템

- 사업관리시스템 로그수집 API(제품 밖) — `interfaces/sf-log-api.md`.
- 전송 이력(Windows PostgreSQL 의 기존 테이블) — `interfaces/sf-log-history.md`.
- sf-daily 전용 DB — 자동 전송 표시와 동시 전송 막기 기록.
- 업체 명부 — `sf-daily/spec/companies.md`.

## 입력

- 업체 코드 · 그날 · 단계 · 보내는 범위의 끝 시각. 모양은 `sf-daily/api/step-sender.md`.
- **설정**
  - 업체 인증키 — `sf-daily/spec/companies.md` 의 업체 표.
  - `SF_LOG_DEFAULT_IP`(기본 `175.193.55.102`, twin.smartline.kr 의 IP) — 로그의 접속 IP 값. IPv4 모양이 아니면 runner 가 시작하지 않는다.
  - `PG_PASSWORD`(필수) · `PG_HOST`(기본 `175.193.55.102`) — 전송 이력 DB 접속. 비밀번호가 비어 있으면 runner 가 시작하지 않는다.
  - `SF_DB_URL`(필수) — `sf-daily/spec/daily-plan.md` 와 같은 전용 DB.

## 출력 (계약)

1. **보내기 결과**: 아래 결과 표의 값 하나와, 보냈으면 사업관리시스템의 결과 코드. 모양은 `sf-daily/api/step-sender.md`.
2. **전송 이력 행**: 사업관리시스템에 요청을 보냈으면 그 요청 하나마다 이력 한 행. 보내지 않은 결과는 이력에 행을 남기지 않는다.

## 핵심 로직 (동작)

### 1. 보내기 전에 다섯 가지를 이 순서로 확인한다

하나라도 걸리면 보내지 않고 그 결과를 돌려준다. 이 표가 확인 순서와 결과의 정본이다.

| 순서 | 걸리는 때 | 결과 |
|---|---|---|
| 1 | 지금의 KST 날짜가 요청의 그날과 다르다 | 지난 날 |
| 2 | 지금이 보내는 범위의 끝 시각 이후다 | 범위 지남 |
| 3 | 앞 단계(업체 명부 단계 표의 바로 앞 순서)의 그날 정상 저장 건수가 0 이다 | 앞 단계 없음 |
| 4 | 이 단계의 그날 정상 저장 건수가 1 이상이다 | 이미 저장됨 |
| 5 | 이 업체로 사업관리시스템에 요청을 보낸 지 10분이 지나지 않았다 | 10분 대기 |

- **로그인 단계는 확인 3 에 걸리지 않는다.**
- **그날 정상 저장 건수는 `interfaces/sf-log-history.md` 가 정한 셈이다.** 자동 전송 · 뷰어 화면 로그인 · Vercel 쪽 전송을 모두 센다.
- **확인 5 의 「요청을 보낸 지」 는 전송 이력에 남은 그 업체의 가장 최근 행으로 잰다.**
- **확인 4 · 5 는 전송 이력과 함께 전송 일지(아래 5절)도 본다.**

  사업관리시스템은 같은 키로 10분 안에 온 두 번째 로그를 저장하지 않는다(AP1029). 그 안에 보내면 시험 결과만 흐린다.

### 2. 보내는 로그의 값은 이 표로 정해진다

| 항목 | 값 |
|---|---|
| 인증키 | 업체 명부의 그 업체 인증키 |
| 로그 일시 | 보내는 그 순간의 한국 시간, `YYYY-MM-DD HH:MI:SS.SSS` |
| 사용 구분 | 업체 명부 단계 표의 그 단계 코드 |
| 시스템 사용자 | 업체 명부의 그 업체 시스템 사용자 값 |
| 접속 IP | `SF_LOG_DEFAULT_IP` |
| 데이터 사용량 | 0 |

- **로그 일시의 날짜는 요청의 그날과 같다.**

  사업관리시스템은 당일 로그만 받는다. 지난 날짜를 채워 보내는 일은 없다.

### 3. 같은 단계는 동시에 두 번 나가지 않는다

- **같은 업체 · 그날 · 단계로 두 요청이 동시에 확인을 통과해도 사업관리시스템에 나가는 로그는 하나다.**

  나머지 요청은 결과 「이미 진행 중」 을 돌려준다.

### 4. 결과는 아홉이고 이 표가 그 정본이다

| 결과 | 뜻 | 이력 행 |
|---|---|---|
| 정상 저장 | 보냈고 결과 코드가 AP1002 | 남김 |
| 오류 응답 | 보냈고 결과 코드가 AP1002 가 아님 | 남김 |
| 전송 실패 | 요청이 사업관리시스템에 닿지 못했거나 응답을 읽지 못함 | 남김 |
| 지난 날 | 확인 1 | 없음 |
| 범위 지남 | 확인 2 | 없음 |
| 앞 단계 없음 | 확인 3 | 없음 |
| 이미 저장됨 | 확인 4 | 없음 |
| 10분 대기 | 확인 5 | 없음 |
| 이미 진행 중 | 3절 | 없음 |

- **이력 행에는 인증키를 남기지 않는다.**

### 5. 보내기 전에 전송 일지에 먼저 적는다

전송 일지는 sf-daily 전용 DB 에 남는, 자동 전송 요청 하나마다 한 건인 기록이다. 업체 · 그날 · 단계 · 요청 시각 · 결과 코드 · 이력 기록 여부를 갖는다.

- **사업관리시스템에 요청을 보내기 전에 그 요청의 일지 건이 전용 DB 에 저장돼 있다.**
- **응답을 받으면 일지 건에 결과 코드를 적는다.**
- **결과 코드가 없는 일지 건(보낸 뒤 결과를 남기지 못함)은 확인 4 에서 정상 저장으로 친다.**

  보냈는지 모르는 단계를 다시 보내면 같은 단계가 두 번 저장될 수 있다. 한 번 덜 보내는 쪽을 고른다. 덜 보낸 단계는 현황 메일에서 0 으로 드러나 사람이 수동으로 보낼 수 있다.

- **결과 코드가 AP1002 인 일지 건은 확인 4 에서 정상 저장으로 친다.**
- **일지 건의 요청 시각은 확인 5 에서 그 업체의 요청으로 친다.**
- **이력 행 쓰기가 실패하면 일지 건에 「이력 미기록」 으로 남기고, 다음 보내기 요청 때 그 행을 이력에 다시 쓴다.**

  이력에 늦게라도 남아야 현황 메일 건수와 이력 화면이 맞는다.
- **자동 전송이 남긴 행은 이력에서 자동 전송으로 구별된다.** 구별하는 값은 `interfaces/sf-log-history.md` 가 정한다.

## 이 모듈에 없는 것

- 언제 부르는가 · 다시 부르는가 — `runner`.
- 그날이 영업일인가 — `business-day` 를 runner 가 먼저 본다.

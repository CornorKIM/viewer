# 2026-11-23 — 영업일 1일 1회 스마트공장 로그 자동 전송

## 배경

- 이 뷰어를 우리 서버(twin.smartline.kr, Docker)에 올려 달라는 요청을 받았다. 원본은 Vercel + GitHub Actions 로도 계속 돈다.
- 사업관리시스템(경기TP 쪽, 로그수집 API)이 정비 중이다. 참여 업체들에게 시험 삼아 데이터를 보내게 하고, 그것을 집계해 데이터량 · 서버 규모를 조사한 뒤 증설과 업체 모집 규모를 정할 예정이다. 다른 공급사들도 같은 방식으로 보낸다.
- 지금은 **데모 기간**이다. "우리는 이런 수집 데이터를 보낼 것"을 보여 주는 견본 전송이고, 생성한 데이터를 보내는 것이 허용된다. 가동 승인이 나면 실제 수집 데이터를 보낸다. 기간은 길다(사람 추정 1~2년).
- 사업관리시스템의 시험 요청 사항: ① 영업일 기준 1일 1회 전송 ② 보내기 전에 이미 보낸 데이터가 있는지 확인 ③ 지난 날은 보내지 않음.

## 정한 것

1. **대상** — 다섯 업체 모두: 유형2-3 목공소봄(A) · 이레공방(B) · 브랜드스미스(C) · 비스트럭처(D), 유형1 (주)씨디알시스템(CDR). 업체마다 자기 인증키로 보낸다.
2. **하루 과정** — 업체마다 하루에 로그인(DO6001) → 데이터 조회(DO6003) → 로그아웃(DO6002)을 한 번씩, 이 순서로 보낸다. 데이터 등록(DO6004)은 보내지 않는다 — 정부 쪽 시험은 로그인 계열이 문제없는지를 보는 것이고, 전력 · 센서 데이터량은 중요하지 않다.
3. **보내는 시각(KST)** — 업체마다 그날의 시각을 아래 범위 안에서 무작위로 하나씩 정한다(업체끼리 로그인 시각이 다르게).
   - 유형2-3(A~D): 로그인 10:00~12:00 · 조회 = 로그인 30분 뒤 ~ 3시간 뒤 · 로그아웃 17:00~20:00
   - 유형1(CDR): 로그인 10:00~11:00 · 조회 = 로그인 30분 뒤 ~ 3시간 뒤 · 로그아웃 17:00~22:00
   그날 정한 시각은 다시 뽑지 않는다(재시작해도 같은 계획). 앞 단계가 그날 정상 저장(AP1002)되지 않았으면 다음 단계는 보내지 않는다. 실패하면 그 단계의 범위 안에서만 다시 시도한다.
4. **영업일** — 월~금이면서 한국 공휴일이 아닌 날. 공휴일은 구글 캘린더 공개 달력 「대한민국의 휴일」(키 없는 공개 iCal)로 판단한다. 설명이 「공휴일」인 일정만 쉬는 날이고 「기념일」(식목일 · 어버이날 · 크리스마스 이브 등)은 쉬는 날이 아니다. 대체공휴일(「쉬는 날 ○○」) · 선거일 · 임시공휴일이 이 달력에 공휴일로 들어온다. 5월 1일은 달력과 상관없이 쉬는 날로 친다. 휴일 판단은 단계를 보내기 직전마다 새로 한다 — 임시공휴일이 갑자기 지정돼도 달력에 올라오면 바로 반영된다.
5. **휴일을 확인할 수 없으면 보내지 않는다** — 달력을 못 받거나 형식이 다르거나 그해 1월 1일 「공휴일」이 없으면(그해 자료 없음) 그 회차는 보내지 않고 사유를 남긴다. 범위 안에서 다음 회차에 다시 확인한다.
6. **이미 보냈는지 확인** — 단계마다 보내기 직전에, 같은 KST 날짜 · 같은 업체 · 같은 구분 코드로 정상 저장(AP1002)된 기록이 공유 DB의 전송 이력에 있는지 본다. 있으면 보내지 않는다. 이 이력은 Vercel 쪽 전송도 함께 기록하므로, 어느 쪽이 먼저 보냈든 한 번만 나간다. 동시에 두 곳에서 도는 경우에도 한 번만 나가도록 선점한다.
7. **지난 날은 보내지 않는다** — 로그 일시는 언제나 보내는 그 순간(KST)이다. 지난 날짜를 채워 보내는 일은 없고, 재시도도 그날 그 시간대 안에서만 한다.
8. **10분 간격** — 사업관리시스템은 10분에 한 건만 저장한다(빠르면 AP1029). 같은 업체의 두 단계 사이는 10분 이상 띄운다.
9. **데이터량** — 보내는 세 단계 모두 0.
10. **보관** — 보낸 모든 건(일시 · 구분 · 사용자 · 접속 IP · 데이터량 · 응답 코드 · 응답 내용)을 공유 DB의 기존 전송 이력 테이블에 남긴다(유형2-3 `tp23.sf_log_history`, 유형1 `tp1.sf_log_history`). 인증키는 남기지 않는다.
11. **뷰어 화면 로그인은 그대로 보낸다** — 사람이 뷰어에서 업체로 로그인 · 로그아웃하면 지금처럼 그때마다 보낸다(다른 브라우저에서 쓰는 실제 사용과 같은 자연스러운 상황). 하루 1회는 자동 전송에 대한 약속이다. 자동 전송은 그날 같은 단계가 이미 정상 저장돼 있으면(화면 로그인이 먼저 저장했어도) 그 단계를 보내지 않고 다음 단계로 넘어간다.
12. **실패는 이력 화면과 23시 현황 메일로 본다** — 오류 응답 · 범위 안에 못 보냄 · 휴일 확인 불가는 이력과 이력 화면(sflog.html)에 드러난다.
13. **23시 현황 메일** — 영업일마다 23:00(KST)에 그날 현황을 메일로 보낸다. 주말 · 공휴일에는 보내지 않는다(전송이 없는 날이라 로그인 0이 정상).
   - 내용: 다섯 업체마다 한 줄, 로그인 · 조회 · 로그아웃 횟수. 횟수는 그날(KST) 정상 저장(AP1002)된 건수다 — 자동 전송과 화면 로그인을 모두 센다.
   - 로그인 횟수가 0인 업체는 빨갛게 표시하고, 메일 맨 위에 "수동 로그인 필요: 업체명"으로 따로 알린다(사람이 수동으로라도 로그인하게).
   - 이력 화면 링크를 함께 넣는다.
   - 보내는 계정: smart-line2 와 같은 Gmail SMTP. 받는 사람: 설정값(지금은 한 명). 계정 · 주소는 .env 에만 둔다.
14. **끝나는 날 없음** — 설정 하나로 끈다. 승인 후 실제 데이터 전송으로 바꿀 때 끈다.
15. **어디서 도는가** — 우리 서버의 Docker 안에서 스스로 돈다(외부 호출에 기대지 않는다). 설정 하나로 켜고 끈다. Vercel 쪽은 건드리지 않는다(저장소 소유자 쪽).

## 왜

- 무작위 시각 · 업체별로 다르게: 사람이 지정했다. 실제 하루 사용처럼 보이고, 단계 사이가 30분 이상이라 10분 간격도 자연히 지켜진다. 10분 제한은 업체(키)별이라 업체끼리 겹쳐도 된다(2026-11-23 다섯 업체 동시 로그인 전부 AP1002).
- 달력 기반 휴일: 코드에 박은 휴일 목록은 임시공휴일을 못 잡는다. 사람이 "주말 · 법정 공휴일 · 임시 공휴일 다 전송하지 말 것"을 요구했다. 공공데이터포털 특일정보 API는 키 발급이 필요해 사람이 구글 달력을 골랐다(키 불필요). 2026-11-23 확인: 2021~2031년 일정, 설명이 「공휴일」/「기념일」로 갈린다.
- 확인 불가 시 보내지 않음: 쉬는 날 보내는 것이 하루 빠지는 것보다 시험 요청 사항 위반이 크다.
- 공유 이력으로 중복 확인: 사업관리시스템에는 보낸 것을 조회하는 API가 없다(연동가이드 · 규격서). 우리가 가진 유일한 근거가 이력이다.

## 기각한 안

- 아침에 한 번에 연속 전송 — 사람이 업무시간 분산을 골랐다.
- 고정 시간표(로그인 08~10 · 조회 10~16 · 등록 16~17 · 로그아웃 17~19, 기존 씨디알 코드) — 사람이 업체별 무작위 시각으로 바꿨다.
- 데이터 등록(DO6004) 포함 · 생성 데이터량 — 사람이 등록 단계를 뺐다.
- 코드에 박은 휴일 목록 — 임시공휴일 누락.
- 공공데이터포털 특일정보 API — 공식이지만 키 발급이 번거로워 사람이 지금은 고르지 않았다. 나중에 바꿀 수 있다.
- 외부에서 시간마다 호출하는 방식(기존 `tp1-auto-ingest` 형태) — 우리 서버에서 스스로 돌면 외부 의존이 없다.

## 열린 것

- 씨디알의 조회 시각 — 사람이 말하지 않아 유형2-3과 같게(로그인 30분 뒤 ~ 3시간 뒤) 두었다. 다르면 바꾼다.
